本节记录用户决定；后文算法、阈值和推进步骤为待验证候选。

## 2. 当前基线与证据边界

2026-10-20 在 `2.0.0` 的 `329e00de` 基线核对：

- 已有出口聚合 v3、64 KiB 历史、训练字典、模板择优与失败退避；不是从“只有 ZSTD”开始。
- 已有实体距离分层、热点密度降频、压力反馈与错峰；`EntityUpdatePacing` 以最近观察者决定实体共享节拍，尚不等于每位观察者独立节拍。
- 1.20.1 Forge 使用旧协议绑定与 SimpleChannel 封装；1.21.1 NeoForge 使用 ProtocolInfo / Payload 注册路径，需分别验原生 codec 与载体封装。
- 既有 26.1.2 工厂采集可用于不透明字节回放；其世界存档不能向 1.x 降级加载，原始字节占比和历史压缩收益也不能当作两个重点版本的新收益结论。
- 既有工厂样本中，模板准入改进主要降低编码 CPU，未证明新增稳定带宽收益。因此继续调模板/压缩等级列为较低优先级对照项。

## 3. 候选工作包

| 编号 | 方向 | 首先回答的问题 | 成本/收益判断方式 |
|---|---|---|---|
| A1 | 高频实体包专用无损编码 | 按字段组织、实体 ID 复用、上一状态预测，能否超过现有历史压缩？ | 同语料、同批次回放，包含附加标记的完整出口字节及 codec CPU |
| A2 | 每观察者独立同步频率 | 能否避免近处一名玩家把远处所有玩家的更新频率一起抬高？ | 近/远观察者混合，多客户端分别计量；验证各自相对位移基线 |
| A3 | 已知 Mod 状态同步适配 | 哪些大流量 payload 确实是可增量的完整状态，而非必须执行的事件？ | 先确定真实流量大户，再逐 Mod 建立语义契约；未知包保持透明 |
| A4 | 长期挂机 / AFK 节流 | 长时间无主动操作的连接，能否减少非必要状态同步并迅速恢复？ | 完整“活动→挂机→恢复”周期的净字节、状态正确性与恢复延迟 |
| A5 | 历史窗口、模板、批次和压缩参数 | 是否还有低成本的通用增益？ | 作为控制组；不得用增大延迟或增加 CPU 隐藏带宽代价 |

A1 的目标是逐包、逐字节无损恢复，包数量、顺序和执行次数不变。A2/A3/A4 可能调整状态更新节拍，必须采用各自的状态一致性标准，不能把它们宣称为原包流完全不变的压缩。

## 4. AFK 节流专项

### 4.1 目标与非目标

目标是减少**该挂机玩家连接的服务端上传量**，尤其是挂机农场、掉落物流和密集实体的长时间同步；游戏世界、机器、实体 AI、掉落物与模拟 tick 按正常规则运行。

不以停止世界模拟、改变农场产出、踢出玩家或清除实体作为节流办法。客户端是否最小化、失去焦点只能作为候选信号，不能直接等同于 AFK；静止观察、GUI 操作和自动化客户端也要纳入误判分析。

### 4.2 待研讨的识别与生命周期

候选流程为 `ACTIVE → IDLE_CANDIDATE → AFK → RESUMING → ACTIVE`；它只是调研模型，不是已定协议。

- 比较显式挂机模式、客户端聚合后的活动提示、服务端可观察的操作三种方案。是否需要双端能力协商、无模组客户端能否参与，分别定结论。
- 区分主动移动/视角操作/交互与水流、载具、碰撞等被动位移；持续移动包或 keepalive 本身不等于用户正在操作。
- 研究进入等待、分级节流、迟滞、最大状态陈旧时间与例外条件；**尚未确定默认开关、时间阈值或具体更新频率**。
- 主动操作、受伤、死亡、传送、维度切换和容器操作等须触发恢复或获得即时处理；列出具体包和顺序，不能只写“重要消息不节流”。
- 按连接维护状态与预算；断连、换维度、重新协商时清理。低 TPS 下的计时口径应明确，不能让 tick 数与实际挂机时长混淆。

### 4.3 同步范围与约束

| 数据类别 | 调研约束 |
|---|---|
| keepalive、握手/能力 ACK、传送确认、连接/配置控制、必要回调 | 维持协议要求的及时性与顺序；不纳入普通 AFK 延迟队列 |
| 玩家自身状态、健康、容器/物品、交互结果及需立即处理的事件 | 明确保活/唤醒策略；不因挂机造成玩法状态错误 |
| 非交互实体的位置、朝向等已知可重建状态 | 优先研究源头降频与每观察者基线；不能在出口随意删除相对位移包 |
| 区块内容、方块实体和光照 | 初版沿用现有正确交付；若进一步降频，须另外定义失效与恢复契约，不依赖尚未实现的方向 B |
| 声音、活塞、动画及未知 Mod payload | 不能按“保留最后一次”通用合并；只有证明语义后才能另列适配 |
| 聚合历史、模板、序号与 FIFO | 不丢弃已经进入编码历史的帧；节流策略与传输状态的交接点必须明确 |

普通玩家和 AFK 玩家同时观察一个实体时，AFK 策略不得降低普通玩家的更新质量。需要变更复制节拍的功能必须按观察者控制，或明确其更保守的可实现边界。

### 4.4 恢复与长期运行

- 恢复时补齐当前状态，避免把长时间积累的过期位置逐包回放；哪些状态可快照替代、哪些事件必须保留，分别定义。
- 为相对移动、实体出生/销毁、metadata、载具关系建立明确基线；实体 ID 复用不得继承旧实体状态。
- 区分“恢复控制已生效”和“视野已完全追平”，分别测量延迟。控制消息及时处理，补齐数据有界调度。
- 测量恢复突发及之后追平流量；不能只截取挂机阶段宣称净节省。
- 给每连接状态表、保留基线、待恢复集合设置可审计上限；超限采用明确的状态重建路径，不无限缓存历史包。

## 5. 实验与验收计划

### 5.1 两个重点组合各自建立原生基线

固定目标版本兼容存档、观察位置、实体/机器工作状态、现有配置、字典和测量时长；保存原始采集及环境信息。现行 `2.0.0` 默认优化为主对照，另设关闭候选功能的控制组。

1.20.1 没有后续版本的 `/tick` 管理命令；现有 `factoryegress` 场景不能原样用于它。需准备目标版本可用的工厂夹具和等价起止/计时方法，保留“机器仍工作”的证据。不能拿 1.21.1 或 26.x 的结果代替 1.20.1 Forge。

### 5.2 场景矩阵

| 场景 | 必查项 |
|---|---|
| 空闲地点与真实工厂，正常活动 | 功能关闭等价、非 AFK 玩家质量、原生 codec 单次执行 |
| 单玩家长时挂机 | 候选 10/30/120 分钟实验窗口；内存、CPU、稳定节流和事件处理；这些时长不是产品默认值 |
| 近处 AFK＋远处活动玩家，以及反向组合 | per-observer 隔离，AFK 不拖慢活动玩家 |
| 静止观察、GUI 操作、被动移动 | 误判率、明确活动时的退出行为 |
| 挂机后操作、受伤、死亡、传送、换维度 | 唤醒、基线重建、恢复突发与可交互时间 |
| 低 TPS、网络延迟、断线重连、功能切换 | 状态清理、FIFO、序号、无长队列和重复执行 |
| 未知 Mod State/Event 混合通道、Bundle、回调 | 不能因类型名称相同误合并事件，顺序与执行次数正确 |

A1 必须检查逐包字节和顺序；A2/A3/A4 必须检查目标状态、关键事件、允许的最大陈旧时间和恢复结果。每项独立 A/B 后再组合，避免把其他功能收益归因给 AFK。

### 5.3 指标与通过依据

- 主指标：服务端最终成功写出的 TCP 载荷，包含协议封装；该口径不含 IP/TCP 头与重传，若另抓线缆字节须独立标注。
- 辅助指标：原始包数/字节、按类型负载、每玩家发送频率、编码 CPU、服务器 MSPT、队列等待、客户端处理成本和每连接内存。
- AFK 特有：误判/退出次数、状态陈旧时间、控制恢复延迟、完全追平延迟、恢复峰值、整个活动—挂机—恢复周期净字节。
- 报告中列出样本重复次数、均值与尾部数据、异常场次和原因；没有重复实测前不承诺百分比。
- 只有两个重点组合分别验证正确性和净收益后，才讨论默认策略；收益小于额外 CPU/延迟成本的候选可停止。
