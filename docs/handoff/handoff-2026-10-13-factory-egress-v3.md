# 26.1.2 氙氪重工 2.0 出口复测

用户提供实际红石工厂存档，要求每次启动恢复 ZIP，避免机器因存储填满停工。此前普通世界的 12–22% 不代表此类负载。本次在 Fabric 26.1.2 使用原生工厂、原有传送门加载器和现有实体降帧配置，没有添加合成实体或测试 Mod payload。

## 场景与可比性

- 输入：`氙氪重工2_0存档.zip`，6,055,143 B，SHA256 `0E3CE592951FF2F48CFA714D58CC0138E050EEEC1EB9958AD4A0D1BFBC1F0CA4`。ZIP 只读，每场恢复到独立 `smoke_fixture_*` 世界；旧副本保留，原存档不修改。
- 静态审计：主世界有 739 黏性活塞、392 普通活塞、1,721 侦测器、3,348 红石线、2,724 漏斗、93 合成器，以及掉落物、矿车、村民和其他实体。原有主世界/下界 portal ticket 均保留。静态数量不表示所有机器同时工作。
- 出生点 Y=-60。工厂 JOIN 显式允许负高度；连接就绪后切观察模式，定位到原玩家附近 `(72.5, 78, 79.5)`。该水平位置覆盖工厂核心，保持原有实体 pacing 生效。
- 世界从首次服务端 tick 起冻结，客户端定位后预热 25 秒，再通过原版 `/tick rate` 和 `/tick unfreeze` 开始计量；测量约 20 秒后再次冻结。这样预热不消耗机器物料。Native 日志确认 TP 和测量起点坐标。
- 每场恢复同一份初始训练字典；level 3、50 ms 等待、262144 B 批次，其余配置相同。场次间自然实体 UUID/玩家名等可能不同；算法比较均使用每场同一份实际原始字节及批次。
- 三场业务门禁 PASS、测量期间协议错误增量 0。原版 Native decoder 实际接收；回放三个模式逐包核对字节和顺序，历史+模板逐字节重现线上选中的帧。每帧均不超过同协议独立字典基线。

## 结果

TCP 口径为服务端 PLAY 成功写出的载荷，包括 vanilla 长度/压缩前缀，不含 IP/TCP 头及重传。独立字典/历史总出口 = 实际 TCP − 实际聚合封装 + 同批次对照聚合封装；旁路流量不变。这是同协议基线，不是无 Hassium 客户端或旧 v2 协议对照。

### 模板与 CPU

计量窗口内三场均为 0 次精确/变量模板引用、0 B 新定义，主要收益来自历史。预热阶段线上已有变量模板命中（1,998 / 1,998 / 1,917），说明模板已进入真实发送路径；工厂运行时完整帧择优没有选中引用。

进一步在同一采集上观测每帧选择前的事务，分别统计匹配候选、拟新增定义和最终完整帧大小。诊断在调用正式 encode 前恢复样本和模板状态，正式编码仍逐字节重现原采集并逐包校验；不改变线上算法。诊断额外执行压缩，耗时不可用于上述 CPU 对照。

| 目标 TPS | 候选精确+变量引用 | 有候选引用的帧 | 模板方案更小的帧 | 拟定义成本 B（未压缩、未发送） | 候选中的新模板引用 |
|---:|---:|---:|---:|---:|---:|
| 20 | 14,261 | 627 | 0 | 270,214 | 13,539 |
| 100 | 63,817 | 2,863 | 0 | 1,177,369 | 59,815 |
| 200 | 72,096 | 3,124 | 0 | 1,305,545 | 68,684 |

100 档候选 7,013 次精确引用、56,804 次变量引用，但所有 2,863 个含引用的候选帧均大于原文输入的最佳完整帧，合计大 796,544 B。这些是被拒绝的候选大小，未产生额外出口量。59,815 / 63,817（93.73%）依赖尚未同步的新模板，反复定义、拒绝、重新建模明显增加计算成本。

定义成本并非唯一原因：额外构造“仅引用已同步模板、其余包发 literal、不增加任何定义”的可解码候选，在 20/100/200 档分别覆盖 121/524/102 帧，仍无一帧小于原文最佳候选。此对照沿用每帧真实选中载荷的历史，不是另一次改变历史轨迹的完整线上试验。

代码目前选择首个可建模的等长样本对、要求至少 8 字节常量，定义包含整包基底及变量槽。工厂主力实体包平均仅约 9–10 B，变化字段和 VarInt 长度变化限制了模板稳定性；64 KiB 历史已复用原始数据重复串。仅用两个样本学到的模板还可能把暂时相等的动态字节当成常量。整帧最终择优能保护出口大小，但当前缺少按模板复现频率、稳定性和预计定义回本成本进行准入的机制，不能据本次零发送引用断言模板本身没有改进空间。

后续应优先评估更稳定的样本分组、多样本变量槽扩展、按定义摊销筛选模板，并对长期败给历史的候选降低计算频率。仍需在同一采集上验证真实完整帧收益，不能通过强制发送更大帧来提升命中数。诊断明细见 [模板候选诊断](factory-egress-v3-template-diagnostic-20261013.csv)，临时诊断源码及完整日志在 `build/analysis/factory-20261013/TemplateDiagnostic.java` 和 `template-diagnostic-{20,100,200}.log`。
完整模式仍计算模板候选，所以 CPU 更高。两条历史轨迹因预热阶段是否采用映射而不同，完整模式比单纯历史多 61/102/158 B，不构成相对独立字典基线变大。

|---:|---:|---:|---:|---:|---:|
| 20 | 115.1 | 299.2 | 782.4 | 816.7 | 328.1 |
| 100 | 74.5 | 268.2 | 725.1 | 725.1 | 1,546.9 |

离线 CPU 按每模式连续阶段计量，排除采集解析和校验；Windows 线程 CPU 时钟约 15.6 ms 分辨率，短阶段/逐作业累加量存在量化误差。在线与离线 CPU 不直接相减；未在线实跑独立字典基线，不宣称端到端延迟改善。以上为单机单次采集，不能作为所有整合包的收益保证。

本存档显示：相同算法在红石/活塞/实体负载下的历史收益高于普通世界；目前自动模板对该工厂没有额外带宽贡献，却增加候选计算成本。后续评估模板准入或计算预算时应以该真实负载为样本，不能强行发送更大的映射帧来制造命中。

## 模板学习与准入改进（同日后续）

按用户要求改动实际发送端算法，而非只改回放。类型/通道和长度分桶，保留跨帧学习模型；选择最少变量的候选，并随多个样本累计变量槽并集。精确模型要求三次观测，变量模型要求两次内容变化，所有常量仍逐字节验证。同批次完成学习后再按最终槽位匹配和估算收益准入，计入引用标志、编号、变量字节和完整定义；最多 16 个新定义，仅完整映射帧胜出才提交。原始包不可变字节在 common 内部复用，避免每次模板查询复制整包。

连续失败退避 1/2/4/8/16/32 帧；前 32 个可学习批次持续学习，之后定期探测。此前未见的类型/长度类别指纹，以及完整原文帧/逻辑载荷大小比的大幅变化，可恢复探测；微小包集合增减不会持续打断退避。此策略减少模型和压缩候选计算，不改变发送顺序、不增加等待、不增加配置键。v3 帧格式和接收端校验未变。

### 同语料完整帧与 CPU 对照

旧 codec 类与源码保存到 `build/analysis/template-admission-20261013/`，基线来自改动前的实际实现。两个策略共用更新后的 `EgressCaptureReplay`，对同一 ZIP 工厂采集、相同原包、批次和训练字典分别运行六遍，丢弃首遍，取后五遍连续阶段的平均线程 CPU 和墙钟。两策略依次运行，避免同时压测；恢复和校验排除在计时外。Windows CPU 时钟仍有约 15.6 ms 量化误差；这是单机离线 codec 对照，未重新启动工厂测 TPS/端到端延迟。

旧策略显式 `verifySelected=true`，逐字节重现所有线上选中帧；新策略显式 `false`，允许发送决策改变，但原包数、每包字节、顺序、CRC 和逐帧独立字典上限均继续强制核对。三个压缩模式、三份采集、六遍均通过。

| 目标 TPS | 旧运行期聚合封装 B | 新运行期聚合封装 B | 新−旧 B | 新−纯历史 B | 整段采集新−旧 B |

运行期三场仍没有映射胜出，也没有新定义。几十到一百多字节的差异来自预热改变了后续 64 KiB 历史轨迹，不能归为新增模板收益。整段含预热、运行和再次冻结，新策略因预热/冻结命中减少，反而多 0.6–1.0 KiB（约 0.03–0.14%）；最终择优仍逐帧不超过独立字典基线，但不保证胜过另一条历史轨迹。预热新策略引用 381/381/100，冻结后 73/1,619/3,651，模板确实仍在实际发送算法中启用。

结论：本工厂语料未验证出额外的模板带宽收益；本次可验证的收益是完整编码 CPU 降低约 52–56%，同时保留对新流量的周期性学习。不能把微小帧差值或更多候选命中当作省流量成果，也不能由此承诺未知 Mod 的收益。
